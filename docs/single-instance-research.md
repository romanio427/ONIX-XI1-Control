# Один экземпляр ONIX: исследование

## Вывод

Установленная и переносная версии должны использовать один идентификатор приложения и один межпроцессный барьер. Первый экземпляр владеет USB, значком в трее и интерфейсом; повторный запуск кратко подключается к нему по IPC, просит показать окно и завершается. Наблюдаемые на снимке 91,0 и 0,9 МБ согласуются с прежней архитектурой: полноценный UI и отдельный лёгкий процесс наблюдения за USB. Это вывод из прежнего кода `startup::watch`, а не измерение конкретных PID со снимка. Разный объём памяти закономерен для разных режимов одного исполняемого файла; Windows показывает приватный рабочий набор процесса, зависящий от загруженных компонентов и активности ([Microsoft](https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-application-service-memory-leaks), [Microsoft](https://learn.microsoft.com/en-us/windows/win32/procthread/process-working-set)).

## Платформы

- **Windows:** именованный `CreateMutexW` с постоянным именем даёт атомарное создание; `ERROR_ALREADY_EXISTS` сообщает о запущенном экземпляре. `Local\\` ограничивает барьер одним сеансом входа, поэтому два пользователя Windows всё ещё могут запустить по экземпляру. Microsoft отдельно предлагает блокировку файла в профиле пользователя для ограничения «один экземпляр на пользователя». Держать handle до завершения, закрывать `CloseHandle`; при гонке между блокировкой и запуском IPC повторять подключение краткое ограниченное время ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw)).
- **Linux/macOS:** держать эксклюзивную блокировку одного файла в пользовательском каталоге данных до завершения. `File::try_lock()` возвращает `TryLockError::WouldBlock`, когда файл занят; `TryLockError::Error` означает другую ошибку I/O, которую следует показывать отдельно. Блокировка освобождается при закрытии дескриптора или `unlock()` ([Rust](https://doc.rust-lang.org/std/fs/enum.TryLockError.html)).
- **macOS autostart:** `SMAppService.mainAppService` регистрирует запуск самого приложения при входе; регистрация LaunchAgent запускает отдельную программу. При требовании одного долгоживущего процесса подходит первый вариант. Apple уточняет, что главный app запускается при последующих входах, а LaunchAgent может стартовать сразу при регистрации ([Apple mainAppService](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp?language=objc), [Apple register](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29)).

## USB и интерфейс

`nusb::watch_devices()` создаёт поток событий; библиотека рекомендует сначала создать watch, затем вызвать `list_devices`, чтобы не пропустить подключение между этими действиями. На Windows событие `Connected` может прийти до готовности интерфейсов составного устройства: попытку открытия следует повторить после небольшой задержки ([nusb](https://docs.rs/nusb/latest/nusb/fn.watch_devices.html)). При ошибке создания watch или завершении его потока один процесс должен повторно подписаться с задержкой и затем пересканировать устройства. Текущий `native/session.rs` уже содержит восстановление после начальной ошибки и `Event::Usb(None)` с ограниченной задержкой; прежний вариант терял слежение. `slint::run_event_loop_until_quit()` сохраняет цикл интерфейса при скрытых окнах; обновления UI из рабочего потока надо передавать через `invoke_from_event_loop` ([Slint](https://docs.rs/slint/1.17.1/slint/fn.run_event_loop_until_quit.html), [Slint](https://docs.rs/slint/1.17.1/slint/fn.invoke_from_event_loop.html)).

## Замечания по текущим изменениям

- Unix-ветка теперь различает занятую блокировку и ошибку I/O.
- При регистрации автозапуска Windows portable-версия сохраняет существующий путь к другой копии, если он ведёт к доступному EXE с новым аргументом `--background`. Запись старого наблюдателя с `--watch-device` заменяется. Установленная версия при своём запуске возвращает путь на себя; установщик останавливает и удаляет прежний `onix-xi1-watch.exe`.
- `--demo` теперь подчиняется общей блокировке. Диагностические команды вроде `--probe` остаются краткоживущими процессами, но не запускают второй долгоживущий экземпляр приложения.
